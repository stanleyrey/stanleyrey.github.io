KlearView — the memory of a mask shop

A photomask passes through a dozen tools on its way to the fab, and every one of them writes down what it saw — in its own format, its own coordinate system, on its own hard drive. KlearView gathers all of it into a single living record, so that a defect first spotted on a bare blank can be followed through writing, inspection, repair and shipping, all the way to the wafer it eventually prints.

I led KlearView's development from the first production deployment through six customer sites, owning the architecture, the full-stack implementation and the release train, and co-authored the SPIE paper that laid out what a mask-shop data system has to be.

The hard part was never storing the data. It was making data from a Lasertec blank inspector, a KLA pattern inspector, a review SEM and a registration tool mean the same thing — one common mask data model, one coordinate convention, with converters for every tool family and MES link in the shop. Once that was true, everything else became possible.

Operators get a single Common Reviewer for every inspector, with native tool images, SEM review, design clips, cutline profiles and CD measurements side by side. Engineers get Defect Source Analysis: a match-up engine that recognizes the same defect across successive inspections, so its whole biography — added, repaired, cleaned, grown — sits on one row. Overlay views stack lots to expose hotspots; cross-database queries join inspection results with process history; scheduled reports hand each mask from the shop's outgoing check to the fab's incoming one.

And the record does not stop at shipping. KlearView collapses wafer inspection fields back onto the mask and matches repeaters to mask defects, so when a fab finds a defect growing under exposure months later, the shop can see exactly what it looked like the day it left.

  1. IngestConverters for a dozen tool families normalize vendor formats and coordinate systems into one schema.
  2. StoreA SQL schema built for 24×7 production, linked to manufacturing databases, with snapshot and replication.
  3. AnalyzeReviewer, DSA, overlay, query and automated reporting — trained once, used on every tool.
  4. Close the loopReticle requal and wafer-to-reticle mapping bring fab results back to the mask that caused them.

EUV Blank Defect Avoidance — hiding what cannot be fixed

An EUV mask blank is a forty-layer mirror polished to atomic smoothness, and most of them still arrive with five to ten defects buried where no repair tool can reach. But a defect under the absorber — the dark part of the circuit pattern — never prints. BDO slides and rotates the entire chip design across the blank until as many critical defects as possible vanish underneath it: a sliding-tile puzzle played at nanometre precision, solved in minutes.

I built the optimization core and the production system around it, and I am the first inventor on the patent. In pilot production it turned mid- and low-grade blanks — the ones a shop would otherwise scrap or gamble on — into masks that yield, lifting yield on affected lots by more than 30% while cutting the cost of incoming material.

The trick is that you cannot hide what you cannot locate. Blank inspectors report positions with 200–300 µm of error, so a safety buffer large enough to be sure would leave almost no blank usable. BDO re-registers every critical defect on a mask registration tool, using bright- and dark-field illumination to pin it down to the sub-30 nm range. Only then is the puzzle solvable.

The solver itself scores each candidate placement on two things: how much of each defect lies on exposed multilayer, and how delicate the pattern it touches is — measured by edge perimeter, because fine, high-MEEF features are hurt far more by the same bump than a wide pad. Defects are weighted by origin, size and repairability, with buried multilayer defects weighing most. A BOBYQA nonlinear search then finds the best shift inside the e-beam writer's ~200 µm window and the best of four 90° rotations, allowing for residual placement uncertainty. In the paper's test case, 8–9 of 13 defects were certain to print before; after, one.

Because the shop keeps a pool of pre-registered blanks in KlearView, every new tape-out is scored against all of them in minutes, and the writer operator simply picks the blank with the lowest risk. The output file carries the shift and the rotation instruction straight to the tool — no manual steps, no transcription errors.

  1. ClassifyAutomatic classification of every blank inspection into critical and non-critical bins, weighted by source and size.
  2. LocateRe-registration on a mask registration tool: from hundreds of µm of uncertainty to sub-30 nm.
  3. OptimizePolygon cost = exposed area + pattern complexity; BOBYQA over shift and 90° rotation.
  4. VerifyAerial-image printability simulation confirms the hidden defects stay hidden.
  5. ChooseA 0–1 score for every unused blank in the database; the operator picks the lowest-risk match.

Applied AI · from prototype to production service

RDC AI Agent — ask the fab a question

A process engineer knows exactly what she wants to know — "which writer produced the lots with the most repeating defects last quarter, and did it change after the PM?" — but the answer is three joins, a coordinate conversion and a chart away, and the one person who can write that query is busy. The RDC AI Agent lets her ask in plain language. It lives inside KlearView, on the fab's own network with no internet access, and answers with real SQL against the production database, a chart and a written analysis, streamed as it works.

I designed and built the service end to end — the agent architecture, the domain knowledge layer that makes a general model fluent in mask-shop vocabulary, and the security envelope that lets a language model work next to production data without ever being trusted with it.

At the centre is a LangGraph ReAct agent behind FastAPI. One routing call reads the question and chooses a skill and a tool sequence: natural-language-to-SQL, decomposition of compound questions into sub-queries and synthesis of the results, data analysis with generated Python, plotting, defect-image retrieval, or plain domain Q&A. Results stream back over SSE as they are produced.

For open-ended questions there is Explore mode: the agent plans, probes the schema, runs SQL and Python, reflects on what it found and iterates — inside a hard token and time budget, keeping a ledger of hypotheses — so it always ends with an answer or an honest "nothing", never a runaway loop. Jobs persist, show their trajectory and can be aborted by their owner.

What makes it right rather than merely fluent is the knowledge layer: schema invariants injected into every call, a lexicon with embedding-based semantic resolution that maps fab terms like writer or illumination to the correct table and key, operator-editable skill documents, and golden-answer fixtures that turn "does the model understand this term?" into a test that runs in CI.

And what makes it safe: JWT identity from the web middleware, host allow-lists, read-only statement preparation where the statement that was checked is the one executed, every line of generated Python run inside an nsjail/Docker sandbox, signed compiled modules and startup integrity checks. 2,600+ unit and quality tests, prompt-regression suites and a single audited surface for every model call keep it that way as it grows.

  1. RouteOne LLM call picks the skill and tool sequence; MCP fallback for anything unusual.
  2. ActRead-only SQL, sandboxed Python, plots and defect images — each tool a contract, each call budgeted.
  3. ExplorePlan → probe → run → reflect, bounded by budget, with a hypothesis ledger and abortable jobs.
  4. GroundSchema invariants, a semantic lexicon and golden fixtures keep fab vocabulary pointing at the right data.
  5. Prove2,600+ tests, prompt regression, harness contracts; every model call through one audited surface.
